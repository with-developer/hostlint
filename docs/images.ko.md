# 컨테이너 이미지 점검

`hostlint scan --image-tar FILE`은 `docker save`(또는 `skopeo copy ... oci-archive:FILE`)로 만든 아카이브에서
컨테이너 이미지의 파일시스템을 점검합니다. 점검 항목과 결과 문서는 호스트나 마운트한 루트(`--root`)를 점검할 때와
같습니다. 아무것도 마운트하거나 실행하거나 쓰지 않으며, 컨테이너 엔진도 데몬도 레지스트리도 필요 없습니다.

```sh
docker save app:1.4 -o app.tar
hostlint scan --image-tar app.tar --fail-on high --format sarif --output hostlint.sarif
```

보고서에는 이미지가 이렇게 표시됩니다. `host.hostname`은 이미지 참조(아카이브의 첫 태그, 태그가 없으면 파일 이름)이고,
`scan.target.root`는 `image:<참조>`이며, `scan.target.kind`는 `--root`와 마찬가지로 `root`입니다.

## 이미지 점검이 보는 것

컨테이너가 시작될 때 보게 되는 파일시스템, 즉 레이어를 쌓아 만든 결과를 점검합니다. 실행 중이 아닌 루트를 점검할
때와 마찬가지로 실행 중의 상태는 알 수 없습니다. 소켓, 실행 중인 서비스, 명령은 `--root`로 점검할 때처럼
`NOT_APPLICABLE`이나 `ERROR`로 보고합니다.

런타임이 나중에 더하거나 정하는 것도 레이어에는 없으므로 보지 못합니다. `/etc/hosts`, `/etc/resolv.conf`,
마운트한 볼륨, 컨테이너를 실행하는 사용자, 권한(capabilities), seccomp, 읽기 전용 루트 파일시스템이 그렇습니다.
따라서 통과는 "이미지의 파일시스템이 이렇게 설정되어 있다"는 뜻이지 "컨테이너가 안전하게 강화되어 있다"는 뜻이
아닙니다.

이미지와 그 이미지로 띄운 컨테이너는 같은 결과를 냅니다. 엔드투엔드 테스트가 지원하는 모든 배포판의 기본 이미지를
아카이브에서 점검하고, 실행 중인 컨테이너 안에서 점검한 결과와 모든 컨트롤·점검 항목을 비교합니다.

컨트롤 중에는 서비스를 돌리고 사람이 로그인하는 호스트를 전제로 한 것이 많습니다. 시각 동기화 서비스, 계정 잠금,
비밀번호 사용 기간 같은 것들입니다. 컨테이너 이미지는 이런 것을 직접 실행하지 않고 호스트가 맡으므로, 이미지에
결함이 없어도 이런 컨트롤은 대체로 `FAIL`이 됩니다. 어떤 기준으로 배포를 막을지는 직접 고르세요.

- `--fail-on high`로 심각도가 높은 것만 막습니다.
- 호스트가 맡는 컨트롤에는 사유를 적은 [예외](configuration.ko.md#예외waiver)를 둡니다. 이미지의 예외는 이미지
  참조를 호스트 이름으로 취급하므로 `hosts: ["app:*"]`처럼 씁니다.
- 이미지에 중요한 컨트롤만 모은 [정책 팩](packs.ko.md)을 씁니다.

`essentials` 프로파일의 커널 매개변수, 방화벽, 자동 업데이트 점검은 이미지에는 해당하지 않습니다.

판단할 수 없는 이미지는 거부하거나 `ERROR`로 보고합니다.

- 운영체제가 없는 이미지(`scratch`나 대부분의 distroless처럼 `os-release`가 없는 이미지)는 거부합니다. 파일이
  없는 것이 통과로 읽힐 수 있기 때문입니다.
- Alpine(`apk` 데이터베이스를 읽는 기능이 아직 없음)과 패키지 데이터베이스가 없는 이미지(distroless, `ubi-micro`)는
  패키지 점검이 `ERROR`로 나옵니다.

## 읽을 수 있는 아카이브

- `docker save` 아카이브와 OCI 레이아웃(`index.json`, `blobs/sha256/...`)을 읽습니다. 레이어는 압축하지 않았거나
  gzip이어야 합니다. 아카이브 자체는 일반 tar여야 하므로 `.tar.gz`는 먼저 풀어 주세요.
- 아카이브 하나에는 이미지 하나, 플랫폼 하나만 담아야 합니다. 이미지가 여러 개 들었거나 멀티 플랫폼 인덱스인
  아카이브는 거부합니다. `docker save --platform linux/amd64`나 `skopeo copy --override-arch`로 하나만 저장하세요.
- `linux` 이미지만 읽습니다. zstd, xz, bzip2 레이어는 건너뛰지 않고 안내 메시지와 함께 거부합니다. 아카이브에
  들어 있지 않은 레이어(URL로 참조)도 거부합니다.
- 다이제스트를 검증합니다. 모든 레이어를 매니페스트(OCI)의 다이제스트와 이미지 설정의 다이제스트에 대조하므로,
  손상되었거나 바뀐 아카이브는 거부합니다.

## 아카이브는 믿을 수 없는 입력입니다

아카이브는 악의적일 수 있으므로 로더는 엄격하게 동작합니다. 모호한 것, 한도를 넘는 것, 컨테이너 런타임이 보는
것과 달라질 수 있는 것은 오류를 내고 점검을 거부합니다. 파일시스템이 일부만 담긴 채로 점검하면 파일이 없음을
확인하는 점검이 통과해 버리기 때문입니다.

- 항목 이름은 런타임이 하는 것처럼 정리하고, 이미지 밖으로 벗어나는 이름은 거부합니다. 심볼릭 링크는 이미지 안에서만
  해석합니다. 하드 링크는 가리키는 파일의 모드와 소유자를 따르며, 민감 경로 거부 목록에 있는 파일로 연결된 하드
  링크도 그대로 거부합니다.
- 레이어는 순서대로 적용합니다. 화이트아웃(`.wh.NAME`)과 불투명 디렉터리(`.wh..wh..opq`)는 레이어 안의 위치와
  관계없이 앞선 레이어의 내용만 지우고, 같은 레이어가 추가한 내용은 남깁니다.
- 한도는 파일 1,000,000개, 아카이브 항목 3,000,000개, 풀었을 때 16 GiB, 경로 4096바이트, 이름 255바이트, 메모리에
  올리는 파일 내용 512 MiB입니다.
- 파일 내용은 1 MiB 이하인 파일과 패키지 데이터베이스(`/var/lib/dpkg/status`, rpm 데이터베이스)의 점검에 필요한
  만큼만 메모리에 올립니다. 그보다 큰 파일은 메타데이터만 보관합니다. 이런 파일을 읽으려 하면 "없음"이 아니라
  "너무 큼"으로 실패하므로, 그 파일이 필요한 점검은 통과하지 않고 `ERROR`나 `MANUAL`이 됩니다.

## 결과를 서버로 보내기

[서버](fleet.ko.md)에서 이미지는 호스트와 별개의 자산입니다. 대시보드에 **이미지** 목록이 생깁니다. 이미지는 일정에
따라 보고하지 않으므로 "오래 보고하지 않음"으로 표시되는 일이 없고, 전체 현황의 호스트 수에도 들어가지 않습니다.

```sh
docker save ghcr.io/acme/app:1.4 -o app.tar
HOSTLINT_TOKEN=hlt_ing_... hostlint scan --image-tar app.tar --push https://hostlint.example.org:8443 --fail-on high
```

이미지는 저장소 이름(`ghcr.io/acme/app`, 아카이브의 참조에서 태그를 뺀 것)으로 구분하므로, 같은 이미지의 여러
태그가 하나의 이력으로 쌓입니다. 스캔마다 태그와 이미지 ID(이미지 설정의 다이제스트)를 기록합니다. 태그 없이 저장해서
이미지 이름이 없는 아카이브는 `--name ghcr.io/acme/app`을 줘야 하고, `--name`은 태그가 있는 이미지의 이름도 덮어씁니다.
CI의 토큰은 접두어에 묶어 두면 토큰 하나가 조직 하나만 다룰 수 있습니다.

```sh
hostlint server token create --name ci --host 'ghcr.io/acme/*'
```

같은 이름이 호스트이면서 이미지일 수는 없고, 이미지에는 호스트 ID가 없습니다. 결과에는 다른 결과처럼 서명할 수
있습니다(`--sign-key`).

## 아직 안 되는 것

- 레지스트리에서 바로 읽기
- zstd 레이어
- 디렉터리 형태의 OCI 레이아웃
- 파일 capabilities(`security.capability`). 이미지에서는 SetID 점검이 이를 볼 수 없습니다.
