# 컨테이너 이미지 점검

`hostlint scan --image-tar FILE`은 `docker save`(또는 `skopeo copy ... oci-archive:FILE`)가 쓴 아카이브에서
컨테이너 이미지의 파일시스템을 점검합니다. 점검 항목과 결과 문서는 호스트나 마운트한 루트(`--root`)를 점검할
때와 같습니다. 마운트도, 실행도, 쓰기도 없고 컨테이너 엔진, 데몬, 레지스트리도 필요 없습니다.

```sh
docker save app:1.4 -o app.tar
hostlint scan --image-tar app.tar --fail-on high --format sarif --output hostlint.sarif
```

보고서에는 `host.hostname`이 이미지 참조(아카이브의 첫 태그, 없으면 파일 이름)이고 `scan.target.root`는
`image:<참조>`입니다. `scan.target.kind`는 `--root`와 같이 `root`입니다.

## 이미지 점검이 다루는 것

컨테이너가 시작할 때 보는 것, 즉 레이어가 만든 파일시스템입니다. 실행 중이 아닌 루트를 점검할 때처럼 실행 중에만
알 수 있는 상태(소켓, 실행 중인 서비스, 명령)는 알 수 없어서 `--root`와 같이 `NOT_APPLICABLE`이나 `ERROR`로
보고합니다. 런타임이 더하거나 정하는 것(`/etc/hosts`, `/etc/resolv.conf`, 마운트한 볼륨, 컨테이너를 실행하는
사용자, 권한(capabilities), seccomp, 읽기 전용 루트 파일시스템)은 레이어에 없습니다. 통과는 "이미지 파일시스템이
이렇게 설정되어 있다"는 뜻이지 "컨테이너가 보안 강화되어 있다"는 뜻이 아닙니다.

이미지와 그것으로 만든 컨테이너는 같은 결과를 냅니다. 엔드투엔드 테스트가 지원하는 모든 배포판의 기본 이미지를
아카이브에서 점검해, 실행 중인 컨테이너 안의 점검과 모든 컨트롤과 점검 항목을 비교합니다.

판단할 수 없는 이미지는 거부하거나 `ERROR`로 보고합니다.

- 운영체제가 없는 이미지(`scratch`, 대부분의 distroless: `os-release` 없음)는 거부합니다. 없는 파일이 통과로
  읽히기 때문입니다.
- Alpine(`apk` 리더 없음)과 패키지 데이터베이스가 없는 이미지(distroless, `ubi-micro`)는 패키지 점검이
  `ERROR`입니다.

## 읽을 수 있는 아카이브

- `docker save` 아카이브와 OCI 레이아웃(`index.json`, `blobs/sha256/...`), 레이어는 압축 없음 또는 gzip.
  아카이브 자체는 일반 tar여야 합니다. `.tar.gz`는 먼저 푸세요.
- 아카이브 하나에 이미지 하나, 플랫폼 하나. 이미지가 여럿이거나 멀티 플랫폼 인덱스인 아카이브는 거부합니다
  (`docker save --platform linux/amd64`, 또는 `skopeo copy --override-arch`로 하나만 저장하세요).
- `linux` 이미지만. zstd, xz, bzip2 레이어는 건너뛰지 않고 메시지와 함께 거부하며, 아카이브에 없는 레이어(URL)도
  거부합니다.
- 다이제스트를 검증합니다. 모든 레이어를 매니페스트(OCI)의 다이제스트와 이미지 설정의 다이제스트에 대조하므로,
  손상되거나 바뀐 아카이브는 거부합니다.

## 신뢰할 수 없는 입력

아카이브는 악의적일 수 있으므로 로더는 엄격합니다. 모호하거나, 한도를 넘거나, 컨테이너 런타임이 보는 것과 다를 수
있는 것은 오류로 점검을 거부합니다. 일부만 담긴 파일시스템은 없는 파일을 점검하는 항목을 통과시키기 때문입니다.

- 항목 이름은 런타임처럼 정리하며, 이미지 밖으로 올라가는 이름은 거부합니다. 심볼릭 링크는 이미지 안에서만
  해석합니다. 하드 링크는 가리키는 파일의 모드와 소유자를 따르고, 민감 경로 거부 목록에 있는 파일로의 하드 링크도
  여전히 거부합니다.
- 레이어는 순서대로 적용합니다. 화이트아웃(`.wh.NAME`)과 불투명 디렉터리(`.wh..wh..opq`)는 레이어 안의 위치와
  관계없이 앞선 레이어의 것만 지우고, 같은 레이어가 더한 것은 남습니다.
- 한도: 파일 1,000,000개, 아카이브 항목 3,000,000개, 풀었을 때 16 GiB, 경로 4096바이트, 이름 255바이트, 메모리의
  파일 내용 512 MiB.
- 파일 내용은 1 MiB 이하인 파일과, 점검이 읽는 만큼의 패키지 데이터베이스(`/var/lib/dpkg/status`, rpm
  데이터베이스)에 대해 메모리에 둡니다. 더 큰 파일은 메타데이터만 두며, 읽으면 "없음"이 아니라 "너무 큼"으로
  실패하므로 그 파일이 필요한 점검은 통과하지 않고 `ERROR`나 `MANUAL`이 됩니다.

## 아직 안 되는 것

이미지 점검 결과를 플릿 서버로 보내기(`--push`는 거부합니다: 이미지에는 호스트 식별 정보가 없습니다), 레지스트리에서
바로 읽기, zstd 레이어, 디렉터리 형태의 OCI 레이아웃, 그리고 이미지에서 SetID 점검이 볼 수 없는 파일 capabilities
(`security.capability`).
